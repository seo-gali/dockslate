# 컨테이너·볼륨·빌드 작업 검증

2026-10-17 기능 검증과 2026-10-18 화면 설정·팝업 최종 검증에 Windows의 실제 DockSlate Tauri 창과 전용 WSL Moby 엔진을 사용했다. 화면 데이터나 백엔드를 모의 구현으로 바꾸지 않았다. 컨테이너·볼륨·빌드 작업과 최종 EXE의 메뉴 이동·전체 새로고침을 확인했다. 아래에는 검사별 실행 범위와 남은 제한을 구분했다.

최종 실행 파일은 `src-tauri/target/release/dockslate.exe`, 4,411,392바이트다. SHA-256은 `4868BF5E7DB5B7EB14C37332C56DAB30AC0BA191BC47297D06DE24AD7A307044`다. 빌드 기록 전송 검사는 이전 실행 파일 `2B79B8BA4F57AA3F8602D631DED33823ADC61885F494F2DD5A0146785159F24B`에서 수행했으며, 각 원시 결과의 실제 실행 파일 정보를 유지했다.

최종 EXE의 메뉴 전환에서 클릭부터 두 번의 animation frame까지 관측한 값은 5.5~13.9ms였다. 수동 새로고침의 `dashboard_snapshot`은 1,312ms, 별도 백그라운드 조회인 `builds_snapshot`은 1,544ms, `containers_metrics`는 1,311ms로 관측됐다. 각 호출의 관측값을 합산해 전체 갱신 시간으로 취급하지 않는다. 이 결과는 해당 실행의 화면 전환·수동 조회 측정이며 앱 시작, WSL 기동, 대용량 목록·로그의 전체 성능을 나타내지 않는다.

볼륨 검증은 `dockslate-e2e-volumes-mvcg6vc8`의 새 원본·복제본만 변경했다. 파일 선택 도우미의 저장 창 식별 실패 뒤 동일한 파일·생성 식별 정보·엔진을 확인하고 내보내기 단계부터 이어갔다. 앞선 5개 검사를 반복해 새 결과처럼 합산하지 않았으며, 이전 실패와 이어하기 정보는 원시 결과의 `resumptions`에 보존했다. 마지막에는 두 볼륨을 정확히 삭제하고 기존 이미지·컨테이너·볼륨이 보존됐는지 확인했다. 전역 prune이나 기존 데이터 정리는 하지 않았다.

빌드 검증은 목록의 `builder/node/id` 전체 참조를 CLI 상세 조회에 그대로 전달하면 실패하는 문제를 찾았다. 선언된 빌더·노드를 검증하고 CLI에는 마지막 ID를 전달하도록 수정했으며, UI의 원래 참조는 유지한다. 처음 2개 검사는 SHA-256 `3004A2E656819B74DC4CA642F11916D710774AD6F3B99A221AB39B1CC9F13897`인 EXE의 PID 304에서 통과했다. 같은 완료 빌드의 이미지·기록·로그를 보존하고 최종 EXE의 PID 16288에서 남은 4개 검사를 이어갔다. 6개 모두를 최종 EXE에서 새로 빌드해 반복한 것은 아니다. 검사별 이전 실패와 이어하기 정보는 [원시 결과](builds-e2e.json)에 있다.

실제 BuildKit이 내보낸 아카이브는 11,439바이트, SHA-256 `7ca076d78c38a98ce41df0c614729408579a946a85a65c7491171be1200f904c`다. 제품 내부 Rust 파서로 가져온 기록의 ID와 격리된 빌드의 고유 로그가 일치했다. 별도 읽기 전용 파서 확인은 `.analysis/genuine-build-archive-preflight.json`에 남겼다. 사용자 빌더는 등록·선택·플랫폼 변경·삭제를 확인했으며 이 빌더로 새 데몬이나 원격 빌드를 시작하지 않았다.

네이티브 Open 창은 전용 STA 스레드 적용 후 같은 파일을 실제로 선택했다. [파일 선택 결과](native-picker-e2e.json). 뒤이어 실제 Open·Save 파일 선택을 포함한 볼륨·빌드 전송 검사도 통과했다. 앞선 권한 오류의 원인이나 보안 제품과의 관련성을 이 관찰만으로 확정하지 않는다.

구현상 제한은 다음과 같다.

- 앱 자체 이미지 빌드는 한 번에 하나씩 실행한다. 진행 중 취소는 지원하지 않는다. 외부 BuildKit 작업 상태는 마지막 조회 결과이며 전체 새로고침으로 갱신한다.
- 원격 BuildKit·TLS·SSH·Kubernetes 경로는 이번 실제 검증에 포함하지 않았다. 사용자 빌더 선택은 앱 실행 중에만 유지하며 재시작하면 검증된 로컬 기본 빌더를 사용한다.
- 볼륨 파일 작업은 옵션 없는 local 드라이버에 한정한다. 약 2.15GB(2GiB), 50,000개 항목으로 제한하며 UTF-8 본문은 65,536바이트까지 표시한다. 링크·특수 파일·다른 마운트는 지원하지 않는다. 새 컨테이너 참조가 확인되면 중단하지만 참조 검사와 파일 변경을 하나의 원자적 작업으로 묶거나 부분 적용을 되돌리지는 않는다.
- 빌드 기록 가져오기는 로컬 기록·로그 보관이다. 이미지나 캐시를 복원하지 않는다. 입력 64MiB, 압축 해제 128MiB, 처리 15초와 보관 메타데이터 제한이 적용된다.
- 실제 VHDX 압축, UAC 승인과 관리자 재실행 성공은 검증하지 않았다. 다른 WSL 배포판 종료·디스크 분리·VHDX 삭제를 수행하지 않았다.
- 사용자 프로젝트의 Compose 파일은 제공되지 않아 해당 프로젝트 전체 빌드 성공은 확인하지 않았다. Kubernetes Deployment와 DockSlate Windows EXE 빌드는 별도 절차다.

작성 중이던 PowerShell 빌드 기록 파서의 보안 탐지는 [별도 기록](build-records-av-incident.md)에 남겼다. 해당 PS1은 실행하지 않았으며 차단 파일 복원이나 보안 설정 변경은 하지 않았다. 오탐으로 판정하지 않는다. 후속 제품 경로는 내부 Rust 파서를 사용하며, 형식 검사 파일의 통과와 실제 Buildx 파일의 E2E는 구분한다.

이번 화면·백엔드는 DockSlate 독자 구현이다. 기존 [Rancher Desktop 1.24.0 REA Evidence](../research/rancher-desktop-1.24.0.md)와 [REA 호출 감사](rea-mcp-call-audit.md)는 보존했고 새 분석 결과로 꾸미지 않았다. 외부 라이선스와 배포 고지의 미확정 사항은 [Third-party notices](../../THIRD_PARTY_NOTICES.md)에 따른다.

테스트에서 만든 컨테이너·볼륨·이미지·빌드 기록과 새 캐시는 정리했고 기존 캐시 11개를 보존했다. [정리 결과](workbench-cleanup.json). 가져온 테스트 기록 두 파일도 해시·기록 ID를 확인해 제거했다. [보관함 정리](imported-build-cleanup.json). 뒤이어 사용자가 만든 `adoring_black` 컨테이너는 팝업·읽기 전용 Inspect와 삭제 승인 취소만 확인했으며 실행·삭제하지 않았다. Compose 검사도 당시 존재한 사용자 컨테이너를 보존했다.

최종 EXE의 읽기 전용 검사를 통과했고, 검증 창을 정상 종료한 뒤 디버깅 옵션 없는 일반 창으로 다시 실행했다. 같은 전용 엔진 ID와 실행 상태를 유지했다. [일반 실행 결과](final-normal-session.json). 글자 크기 기본값은 12px이며 Settings에서 11~16px·다크/라이트를 저장한다. 반복 설명과 개발용 문구를 줄이고 사용법·WSL 보존·Compose·Davit 참고 범위를 [사용 안내](../../USER_GUIDE.md)로 분리했다.
