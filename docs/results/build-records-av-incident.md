# 빌드 기록 파서 보안 탐지

2026-10-17 사용자가 IObit Malware Fighter의 탐지 화면을 전달했다. 대상은 이 작업에서 새로 작성한 `src-tauri/scripts/build-records.ps1`, 표시된 탐지명은 `Heur.BZC.PZQ.Boxter.811.91A39B91`이다. 화면에는 기본 접근 차단이 표시됐다.

작성 에이전트의 도구 이력에 따르면 파일 생성 후 실행 시도는 없었다. 엔진 중지 상태에서도 `.dockerbuild`를 읽으려고 작성한 gzip/TAR/OCI·SHA-256·JSON·protobuf 파서이며, 고정 C#을 `Add-Type`으로 동적 컴파일하는 구조였다. 작성 내용에는 다운로드·네트워크·프로세스 실행·보안 설정 변경·파일 추출을 넣지 않았다고 보고했다. 격리된 원본을 다시 검사하지 못했으므로 이 보고만으로 오탐이라고 판정하지 않는다.

탐지 직후 관련 구현을 즉시 중단했다. 일반 파일 조회에서 해당 경로는 존재하지 않았고, 삭제·격리 여부는 확인하지 못했다. 파일 복원·재작성·이름 변경, 허용 목록 추가, 보안 설정 변경이나 권한 상승을 통한 재시도는 하지 않았다. 이 초기 조사 중에는 작성 중인 새 제품 EXE 빌드도 수행하지 않았다.

기존 EXE는 2026-10-17 17:46:04에 생성된 3,801,600바이트 파일이며, 탐지 후 확인한 SHA-256도 `974A6202AA05F445E63E55603CB5EAE3D4EF70D2E00412E60EC16FB248481DCE`로 이전 검증 기록과 같았다.

이후 PowerShell 파서를 제품 경로에서 제외하고, 동적 컴파일 없이 제품 내부에서 처리하는 Rust 파서를 구현·검증했다. 차단된 파일을 다른 이름이나 경로로 복원해 실행한 것은 아니다.

후속 변경으로 `src-tauri/src/build_archive.rs`에 직접 작성한 Rust 파서를 연결했다. gzip/DEFLATE, CRC32, SHA-256, TAR/OCI JSON과 BuildKit 로그를 제품 코드 안에서 읽으며 외부 프로세스·PowerShell·동적 컴파일·파일 추출을 사용하지 않는다. 입력 64MiB, 압축 해제 128MiB, 처리 15초와 항목·중첩·로그 크기를 제한한다. 엔진이 중지되어도 로컬 기록 가져오기·조회·원본 파일 재내보내기가 가능하도록 연결했으며, 사용하지 않는 Python 파서와 런타임 호출도 제거했다. 차단된 PowerShell 원본은 복원하거나 다시 읽지 않았다.

먼저 Node의 내장 zlib·crypto로 생성한 명시적인 형식 검증 파일을 실제 Rust 실행 파일로 읽어 16개 조건을 확인했다. 비압축·고정·동적 Huffman gzip, 선택 헤더, 메타데이터·로그·해시·시간 일치와 손상·잘림·경로 이탈·중복·링크·protobuf·용량 제한 거부가 통과했다. 이 파일은 BuildKit이 생성한 실제 빌드 결과가 아니며 제품 화면의 데이터로 사용하지 않았다. 결과는 `.analysis/native-build-archive-verification.json`에 기록했다.

후속 검증에서는 실제 앱 빌드에서 BuildKit이 만든 11,439바이트 아카이브를 사용했다. SHA-256은 `7ca076d78c38a98ce41df0c614729408579a946a85a65c7491171be1200f904c`이며, 내부 Rust 파서에서 기록 1개와 고유 빌드 로그가 일치했다. 읽기 전용 확인은 `.analysis/genuine-build-archive-preflight.json`에 있다. Windows 앱의 실제 파일 선택·Buildx 내보내기·Rust 가져오기·기록 조회 경로도 [빌드 E2E](builds-e2e.json)의 6개 검사에서 통과했다. 검사별 실행 파일과 이어하기 범위는 [검증 기록](workbench-verification.md)에 구분했다.

이 후속 성공은 Rust 구현과 해당 아카이브의 실제 동작 결과다. 최초 PowerShell 파일 탐지의 오탐 여부나 포괄적인 안전 판정을 의미하지 않는다. 백신 예외 추가나 보안 기능 변경은 하지 않았다.
