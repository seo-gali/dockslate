## 공개 0.1.3 및 이전 점검

갱신: 2026-10-30 · 개발판 0.1.3. **정식 프로덕션 준비는 여전히 미완료다.** 최신 실행 파일의 [표·선택 목록 검사](table-layout.json)는 22개 통과다. [설치 파일 내부 검증과 다운로드 갱신](release-0.1.3.md)을 완료했다. [0.1.2 UI·실제 예제 검사](ui-cleanup-0.1.2.json)의 15개, 아래 [0.1.1 UI·컨테이너 수정](ui-release-0.1.1.json), [실패 복구](container-edit-recovery-0.1.1.json), [조건부 표·언어·글자 크기](ui-extra-0.1.1.json) 검사는 당시 해시의 범위이며 모두 재실행하지 않았다. 이름 변경은 ID를 유지하고 연결 변경은 파일 보존 이미지·단일 사용 승인 후 재생성한다. 보존 이미지는 기존 파일·환경 변수를 포함하며 볼륨 백업은 아니다.

[정렬·필터·삭제 진행 검사](table-controls-0.1.1.json)도 실제 엔진에서 통과했다. 표시할 행의 선택·순서만 바꾸며 자동 삭제를 추가하지 않았다. 삭제 진행 알림은 요청 ID로 구분하고, 기존 승인·엔진 검증·단일 사용 토큰을 유지한다.

0.1.1에서는 앱 버전과 해당 lock 메타데이터만 올렸으며 의존성 버전·엔진·DB 형식을 변경하지 않았다. 아래 10개 항목의 Compose·DB·CLI 전체 검사는 2026-10-26의 기록이다. 최신 버전에서 모두 재실행했다고 해석하지 않는다. 설치판 내부 파일 검사와 실제 설치·제거 실행도 별도 범위다.

## 이전 통합 점검의 범위

2026-10-26 확인. **정식 배포 준비는 미완료다.** Windows 데스크톱 앱·전용 WSL 엔진을 기준으로 점검했으며, 공개 웹 API를 운영하는 서비스와 적용 범위를 구분했다.

기준은 `main`의 `09f38ef`와 이번 검증·문서 변경이다. 실제 검사한 앱 SHA-256은 `6F7F8DBCDC772951B9F4E2F7AA3BFA3E62CB86F98EA263F5B4FE3B45B3D5DD6B`다. 앱 코드·의존성·lock·배포 패키지를 수정하지 않았다.

2026-10-27에는 개발판 설치 EXE를 갱신했다. 앱 `E20E1E20…`·CLI `30B72789…`를 재컴파일 없이 패키징하고 EXE 내부 바이너리·PATH 도우미·라이선스 375개 파일을 대조했다. [최신 배포 기록](installer-engine-integration.json). 아래 10개 항목 표의 ‘현재 EXE’와 DB 검사는 10월 26일의 `6F7F8DBC…` 범위다. 이번에는 의존성·lock·엔진·DB 형식·환경 변수·IPC 한도·로그 정책을 변경하지 않았다. 새 설치판 실행·전체 회귀·서명·보안 경고 해소·롤백 검증은 여전히 미완료이며, 패키징 성공으로 표의 판정을 통과로 바꾸지 않는다.

| --- | --- | --- |
| 1. 환경 변수·시크릿 | 부분 확인 | [Compose](../../src-tauri/src/compose.rs)는 환경 치환·비밀 파일 참조를 거절하고 격리된 CLI 환경을 사용한다. [Windows CLI](../../src-tauri/src/bin/docker.rs)는 외부 Docker 연결 설정을 제거한다. 비밀 파일 내용·자격 증명·전체 Git 이력의 시크릿 검사는 수행하지 않았다. |
| 2. 오류 처리 | 부분 확인 | 0.1.1의 실제 포트 충돌 재생성 실패 후 원본 ID·이름·설정·실행 상태·파일 복구를 확인했다. 프로세스 시간·출력 한도와 기존 Compose 검사는 유지한다. 디스크 가득 참·강제 종료·복구 자체 실패 전체 시나리오는 미검증이다. |
| 3. 입력 검증 | 부분 확인 | 경로 범위·재분석 지점·서비스 옵션·소스 변경·리소스 충돌 검사 구현을 확인했다. 이번 EXE의 정상 입력은 실제 검증했고, [잘못된 입력 검사](file-import-native-e2e.json)는 이전 EXE 기록이다. 최신 EXE의 모든 부정 입력을 반복하지 않았다. |
| 4. 인증·권한 부여 | 부분 확인 | 0.1.1 수정 명령은 엔진·컨테이너·선택 리소스에 묶인 120초 단일 사용 승인을 적용한다. 미승인·승인 재사용 거절을 실제 확인했다. 로컬 pipe의 SID DACL·원격 연결 거절은 유지한다. 다른 Windows 계정 접근, DB 인증·TLS는 이번 검사 범위 밖이다. |
| 5. DB 마이그레이션 | 적용 범위 확인·미완료 | DockSlate 자체 업무 DB는 없다. [런타임 메타데이터](../../src-tauri/src/runtime.rs)는 JSON `schema: 1`을 검사한다. 실제 MongoDB 쓰기·영속성 성공은 스키마·엔진 버전 업그레이드/다운그레이드 검증을 대신하지 않는다. |
| 6. 로그·모니터링 | 부분 확인 | 앱의 작업 상태·컨테이너 로그·원본 Compose 출력 보호와 출력 한도를 확인했다. 모든 진단 경로의 민감값 마스킹·보관 기간·회전·크래시 수집은 미검증이다. 외부 모니터링 서비스 연동은 없다. |
| 7. 단위·통합 테스트 | 일부 통과 | 현재 EXE의 [기본 Compose 5개](compose-import-e2e.json), [볼륨·포트 8개](compose-volume-port-e2e.json), [실제 MongoDB 8개](compose-mongodb-e2e.json)가 통과했다. 프로젝트는 E2E 우선이며 Rust 단위 테스트는 찾지 못했다. [이전 CLI 전체 검사](native-cli-connection.json)는 32/34 성공·파일 복사 2건 실패로 종료 1이며, 최신 배포본 전체 재검증은 남아 있다. |
| 8. API 속도 제한 | 적용 범위 확인·부분 검증 | 공개 앱 HTTP API는 없다. 로컬 Docker pipe는 최대 32개 인스턴스·31개 작업자, 헤더 64 KiB·일부 JSON 16 MiB 한도가 있다. 초당 요청 수 제한은 없고 IPC 폭주·장시간 연결 부하 검사는 수행하지 않았다. |
| 9. 성능·보안 | 미완료 | CSP·제한된 Tauri capability·고정 구성 요소 해시를 확인했다. 앱·자체 CLI·설치판은 현재도 `NotSigned`이며 [브라우징 데이터 접근 경고](browsing-data-alert.md)의 원인은 미확인이다. 전체 의존성 CVE·침투·장시간 성능 검사는 미수행이다. 라이선스 검사 성공을 취약점 검사 성공으로 해석하지 않는다. |
| 10. 롤백 계획 | 컨테이너 복구 확인·앱 롤백 미완료 | 0.1.1의 포트 충돌 시 원본 컨테이너 복구는 통과했다. 앱 버전 재설치·업그레이드 실패 복구와 DB 데이터 복구 검증을 대신하지 않는다. 이전 정상 릴리스 선정·앱 복구 리허설은 남아 있다. |

## 이번 실제 DB 검사

기존 `trusting_feistel`과 분리된 MongoDB 9.0.4를 앱의 Compose 파일 선택→빌드→승인 실행으로 준비했다. Windows MongoDB Shell 2.14.0이 `127.0.0.1`의 실제 게시 포트로 연결해 문서를 쓰고 읽고 갱신했다. `w: 1, j: true` 응답을 확인했고, 공식 Compose CLI로 테스트 컨테이너를 새 ID로 재생성한 후 같은 문서·nonce·counter를 대조했다.

테스트 컨테이너·이미지·네트워크만 정리했다. DB 삭제·초기화는 없으며 테스트 DB의 볼륨 2개(데이터 210,046,348 B, 설정 0 B)를 보존했다. 기존 컨테이너 ID·상태와 기존 볼륨 메타데이터가 같고 테스트 포트가 닫힌 것을 확인했다. 전용 엔진은 검사 전 중지 상태로 복원했다. DB 인증·TLS·복제·트랜잭션·장애 복구·마이그레이션은 이 검사에 포함하지 않았다.

Windows 클라이언트는 공식 공개 배포 ZIP의 SHA-256과 일치하는 포터블 도구다. 도구 자체 Authenticode는 `NotSigned`이고, 별도 프로필·`--norc`·텔레메트리 비활성화를 사용했다. 프로젝트 의존성이나 배포 파일에는 추가하지 않았다. [도구 출처·해시와 실제 결과](compose-mongodb-e2e.json).

## 롤백 절차

1. 새 릴리스의 버전·앱/CLI/패키지 해시·엔진 ID·기존 리소스 ID와 이전 정상 패키지를 보관한다. 10월 26일 점검 기준은 설치판 `B0B322B1…`, ZIP `B9112C11…`이며 최신 파일의 해시는 [릴리스 명세](../../site/release.json)에서 확인한다. 동일한 파일명이나 `0.1.0` 표기만으로 이전 빌드와 구분하지 않는다.
2. 앱 파일 복구와 데이터 복구를 구분한다. 승인된 앱 종료·기존 검증 패키지 재설치 후 같은 엔진 ID·기존 컨테이너/볼륨·DB 조회를 대조하는 절차를 리허설한다. WSL·VHDX·볼륨을 재설치 과정에서 삭제하거나 초기화하지 않는다.
3. 엔진·DB 포맷·메타데이터 스키마가 바뀌는 릴리스는 호환성과 별도 복원 리허설을 먼저 확인한다. DB 삭제·초기화·운영 스토리지 변경은 별도 대상과 영향에 대한 승인이 필요하다.
